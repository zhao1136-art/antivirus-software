## ⚠️ exe 打开空白事故与修复（2026-07-31 10:47）
**根因**：fix_nav.py 读取 HTML 时用了 `utf-8 失败 → latin-1 回退` 逻辑，index.html 含有 1 个坏字节(0x80)导致 UTF-8 解码失败，走 latin-1 路径 → 整个文件被双重编码（latin-1 解码 + UTF-8 编码），浏览器按 UTF-8 解析全部乱码 → exe 打开首页一片空白。

**修复**：
1. 从 `backend/dist/安盾/_internal/frontend/index.html`（c2=5 正常副本）恢复 `backend/frontend/index.html`
2. 用严格 UTF-8 脚本（禁止 latin-1 回退）从 settings.html 提取导航模板重新统一 index.html
3. 验证 8 页面导航完全一致、全部编码正常
4. 同步到 release/ 和 backend/dist/

**教训（必须遵守）**：
- 处理 HTML 文件绝不使用 latin-1 回退解码！只用严格 UTF-8
- 修改文件前先备份；编码异常时优先从 dist/release 副本恢复
- 统一导航的正确做法：从已知正常页面提取模板 + 严格 UTF-8 读写

## scan_threads 注入检测调优（2026-07-31 10:53）
**问题**：检出 214 ��可疑线程，全部为 ASLR/线程池/模块枚举失败的误报。

**调优方案（inject_guard.cpp 重写 v2）**：
1. 系统进程白名单（System/smss/csrss/wininit 等）直接跳过
2. ntdll 已知线程入口白名单：RtlUserThreadStart、TppWorkerThread、TppTimerpThread
3. 模块范围匹配扩展：记录模块名 + 是否系统模块，入口在模块内 → safe
4. 模块枚举失败的进程降级为 unknown（不告警）
5. 核心判定：只有「MEM_PRIVATE + 可执行」的匿名内存入口才报 high（真正的注入特征）

**验证结果**：
- 误报：214 → **0** ✅（1374 线程全部正确分类）
- 漏报：0 ✅（真实 CreateRemoteThread 注入 jmp$ shellcode 到 RWX 内存 → 检出 tid，region=PRIVATE, risk=high）

**测试注意**：Python ctypes 注入测试必须设置 OpenProcess/VirtualAllocEx/CreateRemoteThread 的 restype=c_void_p，否则 64 位句柄被截断导致测试假失败。shellcode 用 jmp$(EB FE) 保持线程存活，不能用 ret(C3)。
