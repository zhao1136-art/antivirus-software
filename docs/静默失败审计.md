## 0. 先说结论

**问题不是"补丁多"，是"失败没有痕迹"。**

代码里大量"保守选择"（跳过、降级、失败）都被写成了 `pass` / `continue` / `return 默认值`，
**既不记录、也不改变任何可见状态**。于是：

- 用户看到的"没发现威胁"，可能是**真的干净**，也可能是**引擎根本没跑**
- 两种情况的界面表现**完全一致**

这个项目自己已经踩过：见 §2 的 `realtime_guard` 事故注释。

## 3. 四类真问题（均已人工核实）

### A. 静默丢弃 —— 跳过不记账，覆盖率被少报

**A-1 `engine/local_scanner.py:285-286`（已核实）**

```python
                        except (OSError, PermissionError):
                            stats["skipped"] = stats.get("skipped", 0) + 1   # ← 内层：有记账
                            continue
            except (OSError, PermissionError):
                continue                                                     # ← 外层：不记账
```

内层目录项失败会 `stats["skipped"] += 1`，但**外层目录枚举失败直接 `continue`，不计入任何统计**。
后果：某个受保护目录（如 `System Volume Information`）整个没扫，扫描报告里**不会体现**，
用户看到的是"已扫描完成"。

**A-2 `engine/local_scanner.py:314` —— ❌ 原判有误，已撤销**

第一版把 `_should_scan_file()` 里 `getsize` 失败返回 `False` 记为"不计数"。
复核调用方后发现**是计数的**：

```python
elif entry.is_file(follow_symlinks=False):
    if self._should_scan_file(entry.path, scan_type):
        yield entry.path
    else:
        stats["skipped"] = stats.get("skipped", 0) + 1     # ← 返回 False 会走到这里
```

**A-2 不成立。** 保留此条是为了记录"机械扫描的判定必须回到调用方复核"。

**A-3 `engine/scheduler.py:217-220` / `:354`（已核实并已修）** ——
`log_scan_complete` 失败会冒泡到外层 `except`，把**已完成的扫描标成 failed**；
并且有两处调用点，只有一处包了 try。2026-10-25 那次"打包版无法启动扫描"就是
日志异常冒成 500 的同源问题。

**A-4 `engine/quarantine.py:77/159/259`** —— 三处 `pass`（未逐条核实影响）。

### B. 失败被当成"没有命中" —— **最危险的一类**

这类之所以危险：`hit=False` **同时表示**"引擎跑完了、说没有" 和 "引擎没跑成"。
下游只判布尔值就分不清。

**B-1 `engine/cross_check.py:74/92/102/129/133`（已核实）**

```python
    except Exception as exc:
        return {"hit": False, "detail": "不可用: %s" % exc}
```

`detail` 里保留了原因（这点做得好），但 `hit` 是布尔 —— 任何只看 `hit` 的消费方
**无法区分"没命中"和"没跑"**。今天修的闸门二缺陷正属此类。

**B-2 `engine/local_scanner.py:428/673/779`（扫描链路上的引擎异常）** —— 引擎抛异常后返回空结果，
扫描继续，最终 verdict 与"引擎说没威胁"一致。

## 4. 这个项目已经发生过的一次事故

`engine/realtime_guard.py:595` 的注释是本次审计最有力的证据：

> ⚠️ 这里原来是 `except Exception: continue` —— **静默丢弃**。
> 正是它掩盖了"realtime_guard 调用的 `scan_single` 根本不存在"这个致命缺陷，
> 让**实时文件防护长期 0 检测**而界面只显示"没发现威胁"。

一个 `except: continue` 让一个核心功能**长期完全失效而无人察觉**。这不是理论风险。

## 5. 修复模式（不重构，只加"三态"）

核心一条纪律：

> **每一条"跳过 / 降级 / 失败"路径，必须产出一个结构化原因，并且该原因能被看到。**

落地形态很小：

```python
# 现在（二态，无法区分）
except Exception:
    return {"hit": False}

# 改成（三态）
except Exception as exc:
    return {"hit": False, "state": "unavailable", "detail": str(exc)[:200]}
#                          ↑ "miss" = 跑了说没有；"unavailable" = 没跑成
```

配套两件事：

1. **统计必须闭合**：`skipped` / `failed` / `unavailable` 都要计数，扫描结果里回传，
   UI 上可见（哪怕只是在"扫描详情"里加一行"跳过 N 项：权限不足 / 引擎不可用"）
2. **聚合告警**：同一类 `unavailable` 在一次扫描里超过阈值时，**必须让用户看见**，
   而不是继续显示"未发现威胁"

```

```

`confirmed` 的 fail-closed 语义**没有变**（不可用仍然不确认），
只是现在**上层能知道原因**了。
